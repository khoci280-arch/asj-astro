### Temuan inti (semuanya diverifikasi dari kode, bukan tebakan)
Bukan masalah SQL buruk — aplikasi hampir tidak memakai database untuk bekerja:
1. `findAllCandidatesLight()` (db/candidates.ts:89) mengunduh SELURUH tabel via
   loop `for … await` serial (1000/halaman), lalu dedupe/filter/sort/slice di JS.
   5.000 baris = 5 request serial + 1.
2. `findTable()` (db/client.ts:134) menebak nama tabel dengan trial-and-error,
   4–9 probe `select=*&limit=300` berurutan, tiap request yang lewat cache.
   `loadPublicBase()` memanggil `findSettings()` 2× (langsung + via findAssets)
   ⇒ selalu dobel.
3. `Prefer: count=exact` (db/client.ts:120) dikirim di SETIAP halaman ⇒
   full COUNT(*) berulang.
4. `id_loker_pilihan` = CSV dalam satu kolom ⇒ `ILIKE '%kode%'` (wildcard awal,
   btree tak berguna) + rawan salah tangkap TG9ASJ/TG90ASJ.
5. Nomor WA disimpan dalam format campur + 6 alias kolom ⇒ `or=(no_wa.in.…,wa.in.…,
   whatsapp.in.…)` lalu dinormalisasi ulang di JS.

Estimasi: getAppData admin ~2,5–4 s → ~300–600 ms setelah P0+P1 (5–8x).
**Ini estimasi model biaya, bukan hasil ukur** — tidak punya akses produksi.

## LANJUTAN OPTIMASI — Application-Layer Query Fixes (sesi 2)

User: "tolong lanjutkan tadi salah duga optimaze apa yg perlu, gapapa pakai saja
nanti saya ganti passnya" → lanjutkan optimasi kode aplikasi (bukan SQL/index).

### Optimasi yang DITERAPKAN (kode aplikasi):

1. **N+1 FCM token fix** (`actions-schedule.ts` `sendToWaList`):
   Dulu: `for (const wa of waList) { query fcm_tokens WHERE wa = ? }` — N round-trip.
   Sekarang: 1 query `WHERE wa IN (...)` batch. Fallback per-WA bila batch gagal.

2. **SELECT * elimination** (`db/candidates.ts`):
   Buat `CAND_MAP_COLS` = 30 kolom yang dibaca `mapCandidate` (tanpa kolom berat
   yang tidak dipakai). Diterapkan ke: `findCandidatesByIds`,
   `findCandidateByWaFiltered`, `findCandidateByIdFiltered`, `findCandidatesByJobFiltered`.
   Semua punya fallback `SELECT *` bila proyeksi gagal (skema beda).

3. **SELECT * di forms/jobs**:
   `findFormsByWa` (forms.ts) → pakai `FORM_LIGHT_COLS` (sudah ada).
   `findJobByCodeFiltered` (jobs.ts) → buat `JOB_MAP_COLS` baru.

4. **N+1 Storage folder listing** (`actions-share.ts`):
   Dulu: `for (const c of mapped) { await listStorageFolder(folder) }` — serial.
   Sekarang: `Promise.all(mapped.map(...))` — paralel.

5. **Full-table scan elimination** (`actions-schedule.ts`):
   `handleHapusJadwal`, `handleSetTugasStatus`, `handleHapusTugas` —
   dulu `SELECT * limit 500` + `.find()` di JS. Sekarang targeted
   `WHERE id_jadwal/id_tugas = ?` dengan `limit: 1` + fallback `WHERE id = ?`.

6. **Migrasi pendukung** (`netlify/migrations/2026-09-01-optimize-query-indexes.sql`):
   Index untuk pola query baru: `idx_schedule_id_jadwal`, `idx_tugas_id_tugas`,
   `idx_fcm_tokens_wa` ( dokumentasi, sudah ada), `idx_schedule_status_aktif`
   (partial index).

- Semua optimasi punya fallback — perilaku tidak berubah bila skema berbeda.

### Keputusan arsitektur utama (penting — jangan diulang debatnya)

1. **MENOLAK microservices.** Terukur: DB 14 MB, 225 baris kandidat, query
   terlambat 1,8 ms, RTT jaringan 39,2 ms. Jadi 99,7 % latensi adalah jaringan.
   Setiap hop layanan = melipatgandakan satu-satunya biaya nyata.
   Target: **modular monolith dengan batasan ditegakkan** (dependency-cruiser).
2. **24 function bundle → 8 surface sempit.** Semua 24 entry point sekarang
   bundle identik ~331 KB (total 7,9 MB); `ping` pun memuat pdf-parse + xlsx.
3. **12 bounded context.** Aturan CI: context tidak boleh query tabel context
   lain; hanya `repository.ts` yang boleh menyebut nama tabel.
4. **Shared kernel** (timeout, retry+jitter, circuit breaker, bulkhead, log
   terstruktur, cache). Temuan kritis: **transport PostgREST tidak punya timeout
   maupun retry** (`db/client.ts:40,114`) — 1 query hang menghabiskan seluruh
   budget 10 detik Netlify.
5. **CDN sebagai shared cache, BUKAN Redis.** `stale-if-error=86400` membuat
   papan lowongan publik tetap hidup saat Supabase down total.
6. **`job_queue` di Postgres** (SKIP LOCKED + DLQ) menggantikan Kafka di skala ini.
7. **Rate limiter pindah ke Postgres** — `Map` in-process mudah dibypass antar
   instance Netlify.
8. **Klien DB least-privilege**: anon / user-JWT+RLS / service-role allow-list.
